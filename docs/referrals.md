# Referrals: "Invite 3 friends"

A player shares their invite link. A friend who arrives through it, signs up, adds their X handle and plays one verified run counts toward the referrer's three. At three, the referrer gets the soulbound **Recruiter** badge (`trophy:badge:recruiter`) and **300 XP**, once ever.

The game never pays money and never promises it. Any USDC sent to referrers is the owner's own payout through Uprail, by hand, from the admin list (see [The owner's payout](#the-owners-payout)).

This file is the contract between the server (`src/server/db/referrals.ts`, the routes below) and the UI (`/play/invite`, `/invite/[code]`, the account sheet). Where it differs from the first brief, the [Changes from the brief](#changes-from-the-brief) section says so.

## Data (migration `0008_referrals`)

Generated by drizzle-kit from `src/server/db/schema.ts`. **Additive only:** three nullable columns, one new table, two indexes on the new columns. It's safe against the production schema and the code running there today (nothing reads or writes the new columns, and every existing column and index is untouched). There is deliberately **no unique index on `x_handle`**: production may already hold duplicates.

```sql
CREATE TABLE "referral_rewards" (
	"player_id" uuid PRIMARY KEY NOT NULL,
	"goal" integer NOT NULL,
	"friends" jsonb NOT NULL,
	"xp" integer NOT NULL,
	"granted_at" timestamp with time zone DEFAULT now() NOT NULL
);
ALTER TABLE "players" ADD COLUMN "referral_code" text;
ALTER TABLE "players" ADD COLUMN "referred_by" uuid;
ALTER TABLE "players" ADD COLUMN "referred_at" timestamp with time zone;
ALTER TABLE "referral_rewards" ADD CONSTRAINT "referral_rewards_player_id_players_id_fk" FOREIGN KEY ("player_id") REFERENCES "public"."players"("id") ON DELETE cascade ON UPDATE no action;
ALTER TABLE "players" ADD CONSTRAINT "players_referred_by_players_id_fk" FOREIGN KEY ("referred_by") REFERENCES "public"."players"("id") ON DELETE set null ON UPDATE no action;
CREATE UNIQUE INDEX "players_referral_code_key" ON "players" USING btree ("referral_code");
CREATE INDEX "players_referred_by_idx" ON "players" USING btree ("referred_by") WHERE referred_by IS NOT NULL;
```

- `players.referral_code`: unique, null until the player first opens their invite page (`GET /api/referrals`). Postgres lets any number of rows hold null under a unique index, so existing rows are fine.
- `players.referred_by`, `players.referred_at`: who invited the player and when they joined that crew. Set once, ever. Deleting a referrer unattaches their friends (`ON DELETE SET NULL`).
- `referral_rewards`: one row per player, ever. The primary key is what makes the grant idempotent. `friends` holds the qualifying friends' player ids at the moment of the grant.

**The owner applies it to Neon before this branch merges** (every merge to `main` deploys): `DATABASE_URL=… pnpm --filter wgp exec drizzle-kit migrate`. PGlite (local dev, tests) applies it on boot.

## Linking a friend

1. **The landing** (`/invite/[code]`, UI) reads `GET /api/invite/{code}`, stores `localStorage["wgp:ref"]`, and its "Start playing" links to `GET /api/invite/{code}/accept`.
2. **Accept** sets the `wgp_ref` cookie and answers `302 /play?invited=1`. An unknown code (or a banned player's) answers `302 /play` and sets nothing.
3. **Attach.** Every sign-in route (`/api/auth/privy`, `/wallet`, `/near-auth`, `/dev`) calls `attachInviteOnSignIn` once it has its player. It reads the cookie's code, then the body's `ref`, and links the player **only when that request inserted the player's row**. Also refused: an unknown code, a banned referrer, the player's own code, and a referrer this player invited. A bad code never blocks a sign-in.
4. **The cookie is dropped** at the end of any sign-in that carried it: the code either attached, or it never can for this browser's account (a returning player is never re-attached). The UI clears `wgp:ref` after a signed-in response in the same way.
5. **Late claim.** A player who signed up without the link can add their inviter with `POST /api/referrals/claim { code }`, once, within 48 hours of sign-up. Not their own code, and not someone they invited (both rows are locked in id order, so two players claiming each other at once can't both win).

## When a friend counts

A friend counts toward their referrer ("qualified") when **all** of these hold:

1. `referred_by` is the referrer, and neither of them is banned.
2. **X added:** the friend's `x_handle` is set. Handles are compared lowercased without the `@`. A handle equal to the referrer's own doesn't count, and two friends with the same handle count once (whoever joined first).
3. **Played:** at least one run with `runs.status = 'verified'`, in any mode (a ranked night, a case, the Daily, a trial, a duel). Issued, rejected and expired runs don't count.

**X handles are one per player from now on.** `PUT /api/me/social` refuses a handle another player already added: `409 x_taken`, "Another player already added that X handle. If it's yours, remove it from the other account first." A player can always keep the handle they have, even where older rows share it. Saves of one handle take a transaction lock (`pg_advisory_xact_lock`), so two players can't both claim it at the same moment. There's still no unique index.

## The reward

- **When:** the first time a referrer has 3 qualified friends. Once ever.
- **What,** in one transaction (`grantRecruiter`):
  1. `INSERT INTO referral_rewards … ON CONFLICT DO NOTHING`. Only the insert that wins goes on.
  2. Add 300 XP to the referrer's hero in the server-authoritative save, levelling up exactly as a night, a case or an outing does, and bump `saves.rev`. The browser picks it up the way it picks up every server save change: `GET /api/me` returns the new save and rev, and an action sent on the old rev gets `409 rev_conflict` with the new save.
  3. Queue one outbox mint (`mint_reward`, dedupe `badge:recruiter:<playerId>`) with the player's next reward nonce: `{ playerId, accountId, items: [], badges: ["recruiter"], level?, digest }`. `level` rides along when the XP levelled the hero up. `digest` is `sha256("wgp-referral-v1|<referrer>|<sorted friend ids>")`.
- **Held back** (nothing is written, and the next trigger tries again):
  - while the referrer has a run in flight (issued, before its deadline plus the 2-minute grace). That run replays from the save it started with and is written back only if the save hasn't moved, so adding XP under it would void the run (`/api/actions` and the relay refuse save changes then for the same reason);
  - while the referrer has no hero to put the XP on.
- **Idempotency under concurrency:** the save row is locked first (`SELECT … FOR UPDATE`), so concurrent grants for one referrer line up. The primary key decides who adds the XP, and the outbox's unique dedupe key keeps the badge to one row.

### Triggers (no crons)

Each goes through `after()` in `src/server/background.ts` (`checkReferralsSoon`), per player and with no shared window, so every trigger runs:

| Event | Evaluates |
|---|---|
| A run is submitted (`POST /api/runs/:id/submit`) | the player's referrer (when the run verified), and the player as a referrer (their own run ended, which frees a held grant) |
| An X handle is saved (`PUT /api/me/social`) | the player's referrer |
| A late claim (`POST /api/referrals/claim`) | the named referrer |
| The referrer opens their invite page (`GET /api/referrals`) | the referrer, inline, so the page is always current |

A grant from a trigger sends its badge straight away when the operator can mint (`drainRewards`); otherwise it waits in the outbox for the next mint pass.

## APIs

Errors follow the repo's shape: `{ error: "<code>", message: "<for people>", …details }`.

### `GET /api/referrals` (signed in)

`401` signed out, `403` banned, `429` rate-limited (60 a minute per player).

```json
{
  "code": "K7Q2M9X",
  "link": "https://www.wgponnear.fun/invite/K7Q2M9X",
  "goal": 3,
  "qualified": 1,
  "invited": [{ "handle": "nora", "joinedAt": "2026-11-07T10:00:00.000Z", "x": true, "played": false, "qualified": false }],
  "reward": { "state": "locked", "xp": 300, "badge": "recruiter", "tx": null },
  "referredBy": "sele",
  "canClaim": false,
  "self": { "x": true, "played": false, "qualified": false }
}
```

- `qualified` is the count now, and can pass `goal`: cap it in the UI.
- `invited` lists friends in the order they joined, oldest first, at most 100. It shows game handles only, never a friend's X handle or NEAR account. `joinedAt` is when they joined the crew (sign-up, or the late claim). `qualified: false` with both steps true means the handle was already counted, or is the referrer's own.
- `reward.state`:
  - `locked`: not earned yet.
  - `queued`: earned. The XP is in the save, and the badge waits in the outbox.
  - `minted`: the badge is on chain. `tx` is its transaction, for a nearblocks link.
  - `granted`: earned, with no badge row. This isn't expected in practice; show it like `queued`.
- `referredBy`: the inviter's game handle, or null.
- `canClaim`: no inviter yet, not banned, and the account is under 48 hours old.
- `self`: this player's own steps as their inviter's friend, scored by the same rules that count them (`x`: an X handle added; `played`: a verified run; `qualified`: they count). Null without an inviter. The friend side's Tonight checklist reads it, because a hero brought in from the browser carries nights that were never verified runs.

### `POST /api/referrals/claim { code }` (signed in, JSON)

- `200 { "referredBy": "sele" }`.
- `409 already_referred`.
- `422 bad_code | self | too_late | cycle`.
- `400` (no code), `401`, `415` (not JSON), `429`: 8 per 10 minutes per player, 30 per IP.

Codes are read case-insensitively. Spaces and dashes are ignored, and `I`/`L` read as `1` and `O` as `0`.

### `GET /api/invite/{code}` (public, CDN-cached 60 s)

`{ "valid": true, "referrer": { "handle": "sele", "heroName": "The Node", "suit": "classic" } }`. `heroName` and `suit` are null when the referrer has no hero yet. An unknown code, or a banned player's, answers `{ "valid": false, "referrer": null }` with status 200.

### `GET /api/invite/{code}/accept` (public)

`302 Location: /play?invited=1` with `Set-Cookie: wgp_ref=CODE; Max-Age=2592000; Path=/; SameSite=Lax; HttpOnly[; Secure]`, or `302 Location: /play` for an unknown code. Always `Cache-Control: no-store`.

### Sign-in bodies

`POST /api/auth/{privy,near-auth,dev}` and `/api/auth/wallet` (`action: "verify"`) accept an optional `ref` (a string or null, up to 64 characters). It's used when the cookie is missing or its code is bad, and ignored when it isn't a code. The responses are unchanged.

## Admin: `/admin/referrals`

Only for the NEAR accounts in `ADMIN_ACCOUNT_IDS`, with the same gate as `/admin/social`. Everyone else, signed in or not, gets a **404** from the page, the JSON and the CSV, so the page doesn't advertise itself.

- **The list:** referrers with at least one qualified friend, most qualified first. Each shows its game handle, NEAR account, X handle, reward state (with the badge transaction once minted), and its qualified friends with their game handle, X handle, NEAR account, verified runs and join time.
- **Review flags,** per friend, rolled up on the referrer. Each flag carries an icon and a label, never colour alone:
  - **Close sign-ups:** created within 10 minutes of another qualified friend of the same referrer.
  - **Shared X handle:** another player has the same handle (older rows, from before handles became one per player).
  - **One run:** exactly one verified run.
- **CSV:** "Download CSV" (`GET /api/admin/referrals?format=csv`) gives one row per qualified friend with the referrer's columns repeated. The columns are `referrer_handle, referrer_near_account, referrer_x, qualified, reward_state, reward_granted_at, badge_tx, friend_handle, friend_x, friend_near_account, friend_verified_runs, friend_joined_at, friend_flags`. Cells that a spreadsheet could read as a formula are prefixed with `'`.
- **JSON:** `GET /api/admin/referrals` → `{ admin, referrers: AdminReferrer[] }`.
- **The note on the page:** "USDC payouts are sent by the owner through Uprail; this page never pays."

## The owner's payout

The game's part ends at the badge and the XP. A USDC payout is the owner's decision and the owner's action:

1. Open `/admin/referrals` signed in as an admin account.
2. Look at referrers whose reward is earned (`queued` or `minted`). Read the flags: close sign-ups, a shared X handle or one-run friends can mean one person behind several accounts. Check the X accounts by hand where it matters.
3. Download the CSV for the record.
4. Send any payout yourself through Uprail, to the referrer's NEAR account. The game never sends, schedules or names an amount, and its copy never promises money.

## Changes from the brief

The server build owns the contract. These are the places where it now says more than the brief, or something different:

- **`reward.state`** has a normal path of `locked` → `queued` → `minted`. `granted` is defined only as a fallback (earned, no badge row). The UI should show `granted` and `queued` alike, as "earned".
- **The grant is held** while the referrer has a run in flight, or has no hero yet. It goes through on the next trigger, or when they open their invite page.
- **The cookie is dropped** after any finished sign-in that carried it, not only after an attach.
- **Admin refusals are 404,** as on `/admin/social`, rather than 401/403.
- **Codes are made** only on the first `GET /api/referrals`, not at player creation. Typed codes also take Crockford's look-alikes, spaces and dashes.
- **`heroName` and `suit`** are null for a referrer without a hero.
- **`qualified`** can pass `goal`. `invited` is capped at 100 friends, oldest first.
- **`PUT /api/me/social`** refuses a handle another player already added (`409 x_taken`, with `field: "xHandle"`).
- **New admin route:** `GET /api/admin/referrals` (JSON, and the CSV with `?format=csv`).
- **`GET /api/referrals` adds `self`** (a friend's own steps; null without an inviter), so the friend's checklist ticks "Play a night" from verified runs.
